## Resolution

| File | Resolution |
|---|---|
| `spirv_emit_context.cpp` | Both. `define_body` keeps dev's `writes` argument (read-only `native_indirect` bindings in the native bounded pick) and takes #295's three-argument callback (pointer, buffer id, element index). #295's word-split global load/store paths pass `writes` = false/true like their vector siblings; the two atomics keep `true`. One composition fix: the split paths index words (shift 2), so dev's bounded pick (`EDEN_NX2_SSBO_BOUNDS_CHECK`, default on) would have checked only the first word of a 16-byte access. A trailing `tail_words` argument (`count - 1` on the split paths, 0 elsewhere) makes it check the last word, so a split access is picked only when it lies wholly inside the bound length, which is what the vector path's element check guarantees. With `tail_words` 0 no instruction is added: the non-split paths emit the same SPIR-V as before. |
| `vk_rasterizer.cpp` | Both: #295's constructor without `wfi_event`, plus dev's `dynamic_state_flags = DynamicStateFlags();`. |
| `vk_scheduler.h` | Both members: dev's `render_pass_serial`, #295's `compute_writes_pending`. |

The split only triggers when `min_ssbo_alignment` is smaller than the access (AMD, 4 bytes) or for
an immediate offset that is not a multiple of the access size (`VectorViewIsExact`, any device).

## Compute write ordering vs. #215's query wait, `FlushDeferred` and #243

#295 changes only what is recorded into command buffers: the barrier before a dispatch also
covers `DRAW_INDIRECT` (both paths), a dispatch sets `compute_writes_pending` so the next
`BeginRenderPassImpl` records a COMPUTE_SHADER → ALL_GRAPHICS barrier in front of
`vkCmdBeginRenderPass` (at most one per render pass, and every render pass, deferred-clear ones
included, goes through that function), and `WaitForIdle` records a pipeline barrier to
ALL_COMMANDS with a memory dependency instead of the never-reset event. None of it touches the
CPU-side sequencing dev relies on. `FlushQueryResults` (#215) still waits on a fence-manager
operation queued behind `SignalFence`, with `scheduler.FlushDeferred()` submitting between the
bounded slices (`query_wait.h`); `FlushDeferred` only submits the current chunk, and the pending
flag lives on the scheduler, so a submit between a dispatch and the next render pass just moves
the barrier into the next command buffer (barriers order against earlier submissions on the same
queue, so it is still correct). `WaitForIdle` keeps `query_cache.NotifyWFI()` before and
`fence_manager.SignalOrdering()` after, in the same order, and the MoltenVK branch is unchanged.
#243's early macro DMA reads are CPU reads of guest memory on the split front (queued-write
overlay plus report settlement); GPU results reach guest memory only through fence-ordered
downloads, which #295 does not change, so the early-read path and `EDEN_NX2_DMA_READ_EARLY` are
unaffected. `EDEN_NX2_NATIVE_PREFLUSH` (buffer-cache preflush marking) is untouched. Under the
opt-in `EDEN_NX2_PARALLEL_RECORD`, `vkCmdPipelineBarrier` is a serial command, so the new barrier
lands on the primary before the pass begins, like dev's existing pre-dispatch barrier. The cost
side is the WFI barrier, which now actually stalls; it has not been measured on this branch yet.
